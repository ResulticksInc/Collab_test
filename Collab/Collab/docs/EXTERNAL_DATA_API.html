CoLab · Integration guide

External Data API

Connect another platform to CoLab. Read an organization’s data — people, conversations, messages, meetings, tasks, files, or any allow-listed table — and act in it: send messages, receive them on your own URL, place and answer calls, schedule meetings. One API key, plain HTTPS, JSON in and out.

01

What you get

The API sits in front of CoLab’s MySQL database and its messaging, calling and meeting services. Every request carries an API key; the key decides which organization you can see, which scopes you hold, and which user your writes act as. Reads are server-built SQL pinned to that organization. Writes go through the same services the CoLab app uses, so people see them live, get pushed, and your outgoing webhooks fire — exactly as for an in-app action.

Typed endpoints

/users · /conversations · /messages · /meetings · /tasks · /files

Shaped JSON with camelCase fields, related counts (members, attendees) and the filters an integration actually needs: since, status, assigneeId, a date window, and so on.

Shape
Stable, documented objects.
Use for
CRM sync, dashboards, notifications, reporting.

Generic table reader

/tables · /tables/{name}

Row-level reads over an allow-list of tables and columns, with equality filters, a time window and ordering. Snake_case columns exactly as they are in MySQL.

Shape
Raw rows, your choice of columns.
Use for
ETL into a warehouse, BI tools, ad-hoc exports.

Act in CoLab

POST /messages · /webhooks · /calls · /meetings

Send a message to a conversation or straight to a person, subscribe your URL to a conversation’s messages, ring someone and join the call’s media room, or schedule a meeting and invite people — all as a CoLab user of your choosing.

Identity
The key’s actor, or asUserId per request.
Use for
CRM “Message in CoLab” buttons, alerting bots, click-to-call, calendar sync.

Realtime media

LiveKit join tokens

Calls and meetings run on LiveKit. The API returns the same kind of room token the CoLab apps use, so your platform can join the audio/video with the LiveKit client SDK for the web, iOS, Android, Flutter or React Native.

Shape
{ token, wsUrl, room }
Use for
Embedding a CoLab call in your own UI.
02

Get an API key

A key is a string that starts with colab_. It is shown once, when it is created; CoLab stores only a hash and the last six characters so you can recognise it later. Three ways to get one, from least to most privileged.

AAs an organization admin

Sign in to CoLab normally and call the org API with your session token. The key is pinned to your organization and can never read another tenant. You need the org:manage permission (owners and admins have it). For write scopes, give the key an actor (userId) — the member, or a dedicated bot account, whose name your messages and calls will carry.

CA static key in the environment

Keep it secret
The key is a bearer credential: anyone holding it can read everything it can. Put it in your platform’s secret store, never in a URL, a log line or a front-end bundle. If it leaks, rotate or revoke it — the old value stops working immediately.

Every call is a GET to https://<your-colab-host>/api/external/v1/… with the key in a header. Responses are JSON in CoLab’s standard envelope.

Headers

The response envelope

Every success is { ok: true, data, meta? }; every failure is { ok: false, error: { code, message } }. Lists return an array in data and paging information in meta; single objects return the object in data.

Paging

Lists take limit (default 100, max 500) and offset. Keep calling with offset = meta.nextOffset until meta.hasMore is false. There is no total count — it would cost a full scan on big tables. For incremental sync, filter with since (or updatedSince for tasks) and remember the newest timestamp you saw.

Dates

All timestamps are ISO-8601 in UTC (2026-10-14T09:30:00.000Z), both in responses and in query filters. A filter that is not a valid date-time returns 400.

Examples in code

JavaScript / Node 18+page through every message since a timestamp
const BASE = "https://colab.example.com/api/external/v1";
const headers = { "X-API-Key": process.env.COLAB_API_KEY };

async function fetchAll(path, params = {}) {
  const out = [];
  let offset = 0;
  for (;;) {
    const qs = new URLSearchParams({ ...params, limit: "500", offset: String(offset) });
    const res = await fetch(`${BASE}${path}?${qs}`, { headers });
    const body = await res.json();
    if (!body.ok) throw new Error(`${res.status} ${body.error.code}: ${body.error.message}`);
    out.push(...body.data);
    if (!body.meta.hasMore) break;
    offset = body.meta.nextOffset;
  }
  return out;
}

const messages = await fetchAll("/messages", { since: "2026-10-01T00:00:00Z", order: "asc" });

06

Send a message

Post into any conversation the actor is a member of, or straight to a person — the actor’s direct message with them is opened on first use and reused after that. The message is stored, shown live in everyone’s app, pushed to closed tabs and phones, and dispatched to the conversation’s outgoing webhooks and connector bridges, exactly like a message typed in CoLab. Needs messages:write.

Who sends it

Every write runs as a CoLab user. In order of precedence: asUserId or asUserEmail in the body, else the key’s default actor (userId at mint). The user must be a live, active member of the key’s organization — a key can never impersonate someone outside its tenant. With no actor at all you get 400 ACTOR_REQUIRED. A dedicated bot account (“CRM Bot”) keeps integration traffic clearly attributed.

Verify (Node)
import { createHmac, timingSafeEqual } from "crypto";

function verify(req, rawBody, secret) {
  // header: "t=,v1="
  const parts = Object.fromEntries(String(req.headers["x-colab-signature"] || "").split(",").map(p => p.split("=")));
  if (Math.abs(Date.now() / 1000 - Number(parts.t)) > 300) return false;   // 5-minute replay window
  const mac = createHmac("sha256", secret).update(parts.t + "." + rawBody).digest("hex");
  return mac.length === String(parts.v1).length && timingSafeEqual(Buffer.from(mac), Buffer.from(String(parts.v1)));
}
// Answer 2xx fast; do the work after. Non-2xx → retried with backoff.

Deliveries, retries (about 30 s, 2 m, 8 m, 32 m), the full payload per event and the exact signature scheme are specified in Chat webhooks — this API creates the same subscriptions, owned by the actor. Messages the actor sends through this API are delivered too, so de-duplicate on message.id if you echo.

10

Tenants, scopes & actor

Three things on the key decide what a request can do: the organization it is pinned to, its scopes, and the user its writes act as.

Organization key

minted by an org admin, or by the admin portal with organizationId

Pinned to one organization for life. Every query carries organization_id = <that org>. Another tenant’s ids return 404, exactly as if they did not exist. X-Org-Id is ignored.

Platform key

admin portal without organizationId, or EXTERNAL_API_KEYS

Sees every organization, plus rows that pre-date organizations (NULL tenant). Send X-Org-Id: org_… (or ?orgId=) to narrow one request to one organization; an unknown id returns 404. Always send it on writes: a DM, meeting or subscription created without it is stamped with no organization and is then invisible to that organization’s own keys and admins.

The actor

Writes land in tables whose author is a CoLab user, so each write runs as one: the key’s default actor (userId at mint), overridden per request by asUserId or asUserEmail. The user must be live and, for an org-pinned request, an active member of that organization — otherwise 403 ACTOR_NOT_IN_ORG. The actor also needs the ordinary in-app rights for the action (be a member of the conversation, not be blocked by the callee, and so on); CoLab enforces those exactly as for the app.

What is never returned

  • Password hashes, MFA secrets, session or refresh tokens, webhook tokens, connector credentials, other API keys.
  • The body, attachment or voice note of an end-to-end-encrypted message (you get encrypted: true and null). The ciphertext is never exposed either.
  • File bytes. The API returns metadata; download still goes through CoLab’s own authenticated file routes.
  • Avatars (large base64 blobs) and anything soft-deleted.

Writes are limited to what is documented in §06–§09: messages, webhook subscriptions, calls and meetings. Nothing else in the database can be changed through this API.

Rate limits

Each key gets EXTERNAL_API_RATE_MAX requests per minute (default 300), on top of the deployment’s global API throttle. Every response carries X-RateLimit-Limit and X-RateLimit-Remaining; a 429 adds Retry-After. Page with limit=500 rather than many small calls.

14

Integration checklist

  1. Mint a key with only the scopes you need and an expiresAt; name it after the system that will hold it. For writes, give it a dedicated bot account as userId so integration traffic is clearly attributed.
  2. Store the key in your platform’s secret manager. Send it as X-API-Key over HTTPS only.
  3. Call /ping once at start-up and fail loudly if it is not 200 or the organization is not the one you expect.
  4. Page with limit=500 and meta.nextOffset; sync incrementally with since / updatedSince and remember the newest timestamp you processed.
  5. Treat encrypted: true messages as present-but-unreadable; do not retry them.
  6. Prefer a webhook subscription over tight polling to receive messages; verify the signature and answer 2xx within a few seconds.
  7. Never ship the API key to a browser or mobile app. Your backend calls /calls or /meetings/{id}/token and hands only the short-lived LiveKit join token to the client.
  8. Back off on 429 using Retry-After; log the X-Request-Id header on any 5xx so CoLab’s team can find it.
  9. Rotate the key on a schedule and whenever a person who saw it leaves. Revoke it when the integration is retired.
