Chat webhooks

Wire one conversation to the outside world. Send messages into a chat from any system that can make an HTTP request, and get every message out to a URL you control — signed, queued, and retried.

01

The two directions

A direct message is a conversation, so “a webhook for a particular person” and “a webhook for a group” are the same thing with a different kind. Pass conversationId for any conversation you are in, or userId and your existing DM with that person is resolved for you.

Incoming

an external system → a conversation

You get a secret URL. Anything that can POST JSON — a CI job, a monitor, a cron script — posts to it and the text appears in the chat.

Auth
None on the wire. The token in the URL is the credential.
Posts as
The person who created the webhook.
Timing
Synchronous — the response tells you the message id.

Outgoing

a conversation → your endpoint

You give us a URL. Every message in that conversation is POSTed to it, signed so you can prove it came from CoLab.

Auth
Your endpoint decides. Verify the HMAC signature.
Delivery
Queued, at‑least‑once, retried with backoff.
Timing
About a second on a healthy endpoint.
02

Getting your token

There are two different credentials here, and only one of them is an Authorization header. Most integrations never need the header at all after the first day — and where the header is needed, how you get it depends on whether you sign in with a password or through SSO.

What you are doingHeaderCredential
Managing webhooks — create, list, rotate, delete Authorization: Bearer <token> Your normal user session. Expires.
Posting into a chat — /api/webhooks/in/:token none The token already in the URL. Does not expire.
Receiving from a chat n/a — we call you Verify the signature we send.
Key
You need the bearer token once, not on every request. Create the webhook with it, keep the URL it returns, and your unattended system posts to that URL forever with no Authorization header and nothing to refresh. If a script of yours is sending a bearer token on every post, it is calling the wrong endpoint.

If your account signs in with SSO

First
/api/auth/login will never work for an SSO account. It is created with no password at all, and the login route rejects any account without one — so it answers 401 “Invalid email or password.” whatever you send it. That is the design, not a misconfiguration. Your token comes from the end of the SSO round‑trip instead.

The good news: it is the same token. The SSO callback returns the identical { token, user, sessionId, refreshToken } shape as a password login, so everything else on this page applies unchanged.

The round-tripwhere the token appears
1. GET  /api/auth/sso/start        → 302 to your identity provider
2. you authenticate there            ← needs a real browser
3. the IdP redirects back to the app with ?code&state
4. POST /api/auth/sso/callback     { code, state }
5. → { token, user, sessionId, refreshToken }   ← identical shape

Why curl cannot do this on its own. The PKCE verifier is sealed inside the signed state the server minted at step 1, and the IdP session is ended on app logout (/api/auth/sso/logout) — which deliberately pushes you through the provider’s login and second factor on every sign-in. Steps 1 to 3 need a browser and a human. There is no password grant to fall back on.

So take the token out of the browser — once

Sign in to CoLab with SSO as normal, then open the developer console on that tab:

localStorage.getItem("clb_refresh")
// → "rt_9c1f…"  keep this one, it renews the above
OrDevTools → Network
// Find the request made as you signed in:

// Response → data.token
//          → data.refreshToken

On the desktop app the refresh token may live in the OS keychain rather than localStorage, but clb_token always keeps a localStorage mirror, so the console read works there too.

Then
You never need the browser again. POST /api/auth/refresh renews the access token with no identity-provider round-trip at all — so one SSO sign-in is enough to keep a script running indefinitely, as long as it stores each rotated refresh token. And for webhooks specifically you need a token once, ever: create the webhook, then the ingest URL is the credential.

Both
“Renew the token” is the request that keeps you working. It needs no browser and no identity provider, so it is how an SSO user stays signed in to Postman indefinitely — and how an email user avoids re-typing a password. Refresh tokens are single-use; the collection stores the rotated one for you.
Gotcha
CoLab allows a limited number of simultaneous sessions per account (five by default), and every Send of “Sign in” opens another one. Once you hit the limit, signing in returns your list of sessions instead of a token. The collection handles it: it marks the least-recently-used session to be replaced, and you press Send once more. Using “Renew the token” instead of repeatedly signing in avoids the situation entirely.

How long it lasts, and how to renew it

The access token is a JWT valid for 7 days by default (AUTH_TOKEN_TTL). When it lapses, every management call returns 401. Exchange the refreshToken for a fresh one rather than signing in again — and note the refresh token is single‑use, so store the new one it hands back.

No
There are no API keys or service accounts. The bearer token is always a real person’s session, so it expires and it carries exactly that person’s access — which is why a webhook can never reach a conversation its creator cannot. For an unattended system, the incoming webhook URL is the long-lived credential. Don’t park a login password in a CI job to mint tokens on the fly; create the webhook once by hand and give the job only its URL.

Recipe: a button in another app

Your other product has a “Message on CoLab” button. Someone clicks it and a particular person gets a chat message. This is the whole build.

Read

  let url = await db.colabWebhookUrlFor(recipientEmail);

  // First time we've messaged this person — wire them up.
  if (!url) {
    const token = await colabIntegrationToken();   // cached; see step 1

    const [user] = (await get(`/api/users/search?q=${encodeURIComponent(recipientEmail)}`, auth)).data;

      (await post("/api/invites", auth, { toUserId: user.id })).data;

    url = hook.url;
    await db.saveColabWebhookUrl(recipientEmail, url);

  // The click itself: one POST, no auth, nothing to refresh.
  await fetch(url, {
    method: "POST",
    headers: { "Content-Type": "application/json" },

      title: `Ticket #${ticket.id}`,

Three things to expect

BehaviourWhat to do about it

Until they accept, the integration can send text only. No action — incoming webhooks only ever send text anyway.

06

Verify a signature

The signature covers "{timestamp}.{raw request body}". Verify against the raw bytes — a body you parsed and re-serialized will not match, and that is the single most common reason verification fails.

Header format
X-CoLab-Signature: t=1772539134,v1=9f2c4b8e…
                   │            └── HMAC-SHA256(secret, "1772539134.{body}")
                   └── unix seconds, signed too, so a captured
                       delivery cannot be replayed later
Node.jsexpress, raw body
const crypto = require("crypto");

function verify(rawBody, header, secret, tolerance = 300) {
  const p = Object.fromEntries(
    header.split(",").map((kv) => kv.split("="))
  );
  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${p.t}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(p.v1 || "", "hex");
  const b = Buffer.from(expected, "hex");
  if (a.length !== b.length) return false;
  if (!crypto.timingSafeEqual(a, b)) return false;

  // reject a replayed capture
  return Math.abs(Date.now() / 1000 - Number(p.t)) < tolerance;
}

app.post("/colab", express.raw({ type: "*/*" }), (req, res) => {
  const raw = req.body.toString("utf8");
  if (!verify(raw, req.get("x-colab-signature"), SECRET))
    return res.sendStatus(401);
  res.sendStatus(200);          // ack first

Pythonflask, raw body
import hmac, hashlib, time, json
from flask import request, abort

def verify(raw: bytes, header: str, secret: str, tol=300):
    p = dict(kv.split("=", 1) for kv in header.split(","))
    expected = hmac.new(
        secret.encode(),
        f"{p['t']}.".encode() + raw,
        hashlib.sha256,
    ).hexdigest()

    if not hmac.compare_digest(p.get("v1", ""), expected):
        return False

    # reject a replayed capture
    return abs(time.time() - int(p["t"])) < tol

07

Delivery & retries

Sending a chat message never waits on your endpoint. Deliveries are queued and drained in the background, so a slow or dead consumer costs the conversation nothing.

Your endpoint answersResultWhat happens next
2xxdeliveredDone. Recorded in the delivery log with the status code.
5xx, 408, 429retriedBacks off and tries again: roughly 30s, 2m, 8m, 32m — 5 attempts, then permanently failed.
timeout or refusedretriedSame backoff ladder. The timeout is 8s per attempt.
any other 4xxfailedNot retried — an unchanged body will not become valid. Fix the endpoint, then re-run /test.
3xxfailedRedirects are never followed; they would sidestep the address check.

Deduplicate on X‑CoLab‑Delivery if a repeat would matter — delivery is at‑least‑once, so a retry after a timeout you actually processed will arrive twice. And a message that arrived through an incoming webhook is never sent back out, which is what stops an in‑and‑out pair on the same conversation becoming an infinite loop. If you are building a genuine two-way bridge, the far side must originate its own messages rather than echoing what it receives.

StatusMeansFix
400No usable text in the body, or an invalid target URL.Send {"text":"…"}. For a target, use a public https address.
401Missing or expired session on a management route.Sign in again and resend the bearer token.
403You are not a member, or not the creator/admin. On ingest: the webhook’s owner has left the conversation.Re-add the owner, or recreate the webhook as a current member.

503Webhooks are switched off on this deployment.Set WEBHOOKS_ENABLED=true.

When a target URL is rejected

An outgoing target is a URL the server fetches, so it is refused if it resolves into loopback, link-local (including the cloud metadata address), private or carrier-NAT space — and that check runs again on every delivery attempt, because DNS can be repointed after you register.
