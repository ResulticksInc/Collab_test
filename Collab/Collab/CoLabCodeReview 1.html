Enterprise readiness assessment

Six independent reviewers swept ~130k lines of TypeScript across security, feature completeness, architecture and operations. Every finding was then re-checked by an adversarial verifier against the actual code; refuted ones were dropped and inflated severities corrected.

Overall
Not production-ready

Not deployable as a Teams replacement today. CoLab is a genuinely ambitious, largely real implementation — the chat pillar, the LiveKit call stack, the session/MFA engine and the exactly-once schedulers are production-shaped work — but it ships with four unauthenticated or near-unauthenticated account-takeover and cross-tenant paths (hardcoded ops password in the production compose, data:text/html avatars, share-links granting every user in every org, NULL-org sessions disabling all tenant filters), and the document-sharing and calendar pillars a Teams replacement is bought for are either hidden in the shipped UI or absent (no .ics, no Outlook interop, no recurring occurrences on the calendar). It is defensible today only as a closed pilot for a single trusted tenant of a few hundred users on an isolated network, with signup disabled, the ops portal password set, and the file share-link feature turned off — and only after the two stored-XSS routes are fixed.

The five things that would actually hurt

Ordered by real-world blast radius, not by how easy they are to fix.

  1. 1

    Internet-reachable engineering portal with a password published in the repo. docker-compose.production.yml:106 and docker-compose.live.yml:155 default OPS_PORTAL_PASSWORD to `CollabOps!2026`, and the boot-time weak-secret guard in backend/app/src/index.ts deliberately does not cover it — so an unauthenticated attacker gets error logs with request paths, user names and emails, E2EE device inventory, container state and the running config.

  2. 2

    Two stored-XSS primitives on the app origin, one of them unauthenticated end-to-end. backend/app/src/routes/public.ts:16 echoes a user-controlled `data:` Content-Type verbatim (so `data:text/html` renders attacker HTML at /api/public/users/<id>/avatar with no auth), and backend/app/src/routes/media.ts:168 serves user-uploaded image/svg+xml inline; either one reads localStorage.clb_token and takes over any account, including org admins.

  3. 3

    Tenant isolation fails open, and self-service signup is the way in. database/src/drivers/mysql.ts:351 applies the org predicate only when the session carries an orgId, and a self-registered user has none — so their first GET /api/users returns every user row across every tenant with email, phone, title and presence. The COLAB_ORG_GUARD tripwire meant to catch missed filters is off in production.

  4. 4

    One share link grants the whole deployment. backend/app/src/services/fileService.ts:186 folds `meta.linkPermission` into the effective permission for every authenticated caller with no token and no tenant check, so clicking 'Copy link' on a confidential document silently grants download — and, at permission 'edit', re-share — to every user in every org.

  5. 5

    There is no way to operate this in production. No structured logging, request IDs, metrics endpoint or tracing anywhere (infrastructure/monitoring/README.md is a five-line placeholder); CI's unit tests, secret scan and dependency audit are all continue-on-error (.github/workflows/web-build.yml:102) so only typecheck and `next build` block a merge that then auto-publishes :latest; there is no root package-lock.json even though both Dockerfiles run `npm ci`; and backups are a manual shell script with no off-box destination.

Teams-parity feature matrix

Solid means production-usable as-is. Counts: 2 solid · 10 partial · 6 weak · 2 missing.

Solid Chat/Messaging

The most complete pillar: 1:1/group/channel, tombstones plus delete-for-me, forwarding, scheduled messages, voice notes, correct composite keyset pagination, and every mutation gated by one assertMember helper — marred only by fire-and-forget send that shows a Sent checkmark on a 400ms timer even when the server rejected it (useCoLab3.tsx:267).

Solid Notifications & Push

In-app, socket fan-out and Web Push with VAPID, per-recipient quiet-hours and notifyLevel gating, per-conversation mute applied before send, and automatic pruning of 404/410 stale subscriptions; the caveats are @mention inserts running in a detached promise with a bare catch, and push clicks into hidden modules landing on the dashboard.

Partial Threads & Reactions

Inline threads, reactions, pins, bookmarks and importance flags are all implemented and membership-gated, but MESSAGE_REACT broadcasts to a client-supplied room id, letting a user inject a fully serialized message from one conversation into another (realtime/socket.ts:723).

Partial Presence

Presence and typing work and meeting presence is TTL-based so crashed tabs leave no ghosts, but typing indicators and read receipts can be injected into any conversation by any authenticated user who knows the id (realtime/socket.ts:750), and presence fans out only within a replica when the Redis adapter silently degrades.

Partial Audio Calls

Real SFU-backed signalling with an atomic busy/glare check at request time, but state transitions are read-then-write so accept/decline/cancel glare produces contradictory events, and a user signed in on two devices cannot answer at all — the devices evict each other and the loser ends the call for both parties (useCoLab6.tsx:131).

Partial Video Calls

Simulcast, dynacast, adaptive stream, device hot-swap with setSinkId fallback and a bounded token-re-minting auto-rejoin are all real; the same two-device answer bug and the missed-call timeout living only in process memory (a lost replica leaves both users permanently flagged busy) are the blockers.

Partial Screen Share

Screen share works with presenter-mode compositing and Electron-native remote control, but LiveKit tokens grant canPublish unconditionally (livekitService.ts:86), so there is no 'only organizers and presenters can share' and nothing stops an attendee sharing over the presenter.

Partial Meetings & Lobby

Lobby, lock, persisted eject, co-hosts, raise-hand, in-meeting chat and whiteboard are all implemented, but lobby is off by default and enterRoom self-enrolls any org member who has the UUID as an accepted attendee with permanent recording access (meetingService.ts:374); an ejected user can replay a cached 1h token straight back into the SFU.

Partial Tasks

Surprisingly deep — projects, saved views, subtasks, multi-assignee, watchers, deps, CSV export, and optimistic locking wired end-to-end from SQL to a 409-reconciling client — but the module is hidden in the shipped frontend and several write paths (subtask toggles, bulk ops) bypass the version guard and clobber concurrent edits.

Partial SSO/SAML

OIDC Authorization Code + PKCE S256 with an HMAC-signed TTL-bounded state and a production guard that makes the insecure-skip-verify escape hatch throw, but the nonce is only enforced when the id_token happens to carry one and state is not bound to the browser, giving a login-CSRF path that seats a victim inside the attacker's account. No SAML.

Partial MFA

The implementation is the strongest crypto in the repo — HKDF purpose-separated keys, GCM-sealed seeds, HMAC'd backup codes, RFC 6238 replay protection, fail-closed on unreadable enrollment — but it is disabled by default (MFA_ENABLED=false) and /auth/sessions/evict skips the step-up entirely, so a stolen password alone can force a victim offline.

Partial Admin/Org Management

RBAC is genuinely careful — server-resolved /current/* addressing, requirePermission failing closed on missing org, and grantablePerms preventing privilege minting — but the tenant boundary underneath rests on ~60 hand-written predicates that fail open on a NULL-org session, and the error ledger read/write is permission-gated but not tenant-scoped (mysql.ts:4622).

Weak Search

FULLTEXT search ignores the per-member history cutoff and delete-for-me, returning pre-join message bodies to users explicitly added without history (mysql.ts:1397); with E2EE on — which .env.example enables — body is NULL so search returns zero results forever; file hits are stripped because Files is hidden.

Weak Recording

Client-side canvas composite plus Web Audio mix is a real implementation, but it buffers in browser memory with no bitrate cap against a 300MB body limit, so anything past ~15-20 minutes is rejected and irrecoverably lost (routes/meetings.ts:807), and playback advertises Accept-Ranges while ignoring Range, forcing the whole file into a blob with no seeking.

Weak Document Sharing

The backend pipeline, permission model, recycle bin and TOCTOU-safe GC are solid, but the entire Files module is hard-disabled in the shipped frontend (hiddenModules.ts:17) so effective sharing is chat attachments only — and creating a share link grants the file to every authenticated user in every org (fileService.ts:186).

Weak Calendar & Scheduling

The DST-correct recurrence rule engine is well built and drives reminders correctly, but expandOccurrences has zero callers so a series shows on its first date only (meetingService.ts:169), RSVP/edit/cancel apply to the whole series with no per-occurrence exceptions, and there is no free/busy lookup — conflicts are computed client-side over already-loaded meetings.

Weak E2E Encryption

Real code but self-contradictory state — the disablement directive says OFF while .env.example turns it ON — and turning it on silently kills message search, AI summaries and push previews; ~1,000 lines of orphaned E2EE modules ship in the bundle including a recovery stub that returns true for a key recovery that never happened, and scheduled messages store plaintext server-side regardless.

Weak Mobile/Desktop clients

An Electron desktop wrapper exists (and is the only place with a lockfile) and drives native input injection for remote control, but running it alongside a browser tab is exactly the two-device state that breaks 1:1 call answering; there is no mobile client, and PRESENTER_MODE.md advertises MediaPipe assets under a public/ directory that does not exist in the repo.

Missing Document Co-editing

No co-authoring of any kind, no versioning, no previews or thumbnails, no quotas, and virus scanning is an explicit no-op stub with a comment saying so (virusScanService.ts:44); the only real-time collaborative artifact in the product is the meeting whiteboard.

Missing External Calendar (.ics/Outlook) Interop

Confirmed by grep: no VCALENDAR emission, no .ics generation, no email invite delivery and no Exchange/Google/CalDAV sync anywhere in the repo; attendees are CoLab user ids only, so external participants cannot be invited and an Outlook user is never told a meeting exists.

Attacker signs up (self-service signup is on by default — config/src/index.ts:37 `signupEnabled: bool("AUTH_SIGNUP_ENABLED", true)`), sends PATCH /api/users/me with {"avatarUrl":"data:text/html;base64,<script that exfiltrates localStorage>"}, then posts the link https://<host>/api/public/users/<their-id>/avatar into any chat. Recommendation

Evidence

backend/app/src/middleware/auth.ts:145 verifies it successfully (`const p: any = authService.verify(token);`) and backend/app/src/services/authService.ts:611-613 does no claim validation at all:

auth.ts never checks that `sub` exists — line 244: `req.user = { userId: p.sub, name: p.name, deviceId: p.deviceId || null, jti: p.jti || null };`
With no `jti`, the session check (auth.ts:208) and lazy-org adoption (auth.ts:225) are both skipped, so `(req as any).org` is null (auth.ts:272). E2EE is off by default (config/src/index.ts:239 `enabled: bool("E2EE_ENABLED", false)`), so the device-binding branch is a no-op.
Downstream, an undefined org means "no filter" — backend/app/src/routes/users.ts:16-18: `res.json(ok((await db.users.list((req as any).org?.id)).map(pubUser)))`, and database/src/drivers/mysql.ts:356-364: `const orgClause = orgId ? " AND EXISTS (...)" : "";` … `SELECT * FROM users WHERE deleted=0${orgClause} ORDER BY name`.
Note fileService.ts:278-281 shows the team was aware of this exact hazard for download tickets ("carries a distinct `purpose` and NO `sub` claim, so … it can NEVER authenticate as an access token") — but the ops token got no equivalent treatment on the verifying side.

Impact

An ops-portal token (obtained from `POST /api/ops/auth`, i.e. with the hardcoded default password above) can be replayed as `Authorization: Bearer <ops-token>` against the normal product API. `GET /api/users` then returns every non-deleted user across every tenant with full profile PII, because `orgId` is undefined and the org-scoping clause is dropped. More generally, authMiddleware constructs a `req.user` whose userId is `undefined` and lets the request proceed, so any handler where an undefined id degrades to "unscoped" becomes an access-control failure. There is no key separation: one AUTH_JWT_SECRET signs app access tokens, ops tokens, file-download tickets (fileService.ts:290), the SSO state HMAC (config/src/index.ts:89-92) and the MFA seed/challenge keys (mfaService.ts:44).

Recommendation

Reject tokens without a `sub` in authMiddleware (`if (!p.sub) return 401`) and add a token-type claim (e.g. `typ: "access"`) that is asserted on verify. Pin algorithms/issuer/audience in `authService.verify` (`jwt.verify(token, secret, { algorithms: ["HS256"], issuer, audience })`). Give the ops portal its own signing secret (OPS_JWT_SECRET) rather than reusing config.auth.jwtSecret.

I read authMiddleware in full (auth.ts:138-278) looking for a guard: there is NO check of `scope`, `purpose`, or the presence of `sub` — grep for scope/purpose in that file returns only comments.
