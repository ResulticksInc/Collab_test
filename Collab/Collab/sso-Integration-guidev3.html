Single Sign-On (SSO) Integration — CoLab

OpenID Connect (Authorization Code + PKCE) against the shared AgenXchange Identity Provider. Every code sample below is the real CoLab implementation (Node/Express backend, Next.js web app, Electron desktop sharing the same endpoints). Values marked «per-env» differ between local, teams and run.

Aligned with AgenXchange guide v3: IdP host https://stgoa.re.cx/, OIDC claims request for the full profile pack, RSA claims_jwe decryption (PEM exchange), IdP launcher login_hint, RP-initiated logout.

What CoLab implements from guide v3 (and what it deliberately does not):
  • IdP base URL https://stgoa.re.cx/ — one env var (SSO_BASE_URL) derives /authorize, /token, /jwks, /logout.
  • Authorize requests carry the OIDC claims parameter asking for email, name, picture, department, employee_id, claims_jwe, products, entitlements.
  • RSA claims_jwe is decrypted server-side with jose and CoLab's private PEM (keys/collab_private.pem). AgenXchange encrypts with keys/agenxchange_public.pem. Decrypted values override plaintext claims.
  • The IdP picture seeds the user's avatar; department / employee_id ride on the profile.
  • IdP launcher ?login_hint= on the app root auto-starts OIDC — never the password form.
  • Logout ends both sessions: app session revoked, then a full-page trip through the IdP /logout.
  • Fernet *_enc copies are decrypted with SSO_PROFILE_ENC_SECRET (Node port of the Fernet spec, cross-checked against Python cryptography); /userinfo is consulted when the id_token carries no identity. Resolution order: id_token → userinfo → *_enc → claims_jwe, decrypted values win.
Three environments, one client. The app host is the redirect_uri (app root, no trailing slash):

The IdP answers HTTP 400 to an unregistered redirect_uri before showing its login page, so a missing registration looks like "SSO does nothing". Each environment signs its own OAuth state, so a code returned to the wrong host is always rejected.

All teams use ONE shared IdP: https://stgoa.re.cx/ for /authorize, /token, /jwks, /userinfo, /logout. Discovery at /.well-known/openid-configuration publishes issuer = https://stgoa.re.cx, id_token_signing_alg = RS256, claims_jwe_alg = RSA-OAEP-256, claims_jwe_enc = A256GCM. CoLab registers as client collab (confidential, PKCE always on).

1. Concepts to know first

IdPCentral Identity Provider at stgoa.re.cx (AgenXchange "Saavee" login) that owns user credentials. CoLab never sees a password.
ClientCoLab. Registered on the IdP as client_id = collab with a client secret (server-side only).
redirect_uriThe app root of the environment (table above). Pre-registered; byte-for-byte match, no trailing slash.
codeShort-lived, single-use authorization code the IdP appends to the app root; the SPA posts it to the backend, which swaps it for tokens.
PKCEcode_verifier + code_challenge = S256(verifier). Always on, even with the client secret.
stateAnti-CSRF value echoed back. CoLab HMAC-signs it (10-minute TTL) and embeds the PKCE verifier + nonce, so no server storage is needed across instances.
nonceBinds the id_token to the login CoLab started (replay protection).
claimsOIDC claims request parameter on /authorize: JSON naming the profile fields CoLab wants in the id_token and at /userinfo, including claims_jwe.
claims_jweCompact JWE (RSA-OAEP-256 / A256GCM) whose plaintext is a JSON object with the PII. IdP encrypts with CoLab's public PEM; CoLab decrypts with its private PEM.
login_hintEmail the IdP app launcher appends when opening the CoLab homepage (no code yet). CoLab starts OIDC with that hint.
app sessionCoLab's own JWT (+ rotating refresh token), returned in the JSON body of the callback exchange — never in a URL. Stored in localStorage (web) or the OS keychain (desktop) and bound to the device's E2EE identity.

Step 3 — PKCE helpers

backend/app/src/services/ssoService.ts — pure Node crypto, no extra dependency:

import { createHash, randomBytes } from "crypto";
function b64url(buf: Buffer): string {
  return buf.toString("base64").replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/g, "");
}
export function randomString(byteLen = 48): string {
  return b64url(randomBytes(byteLen));
}
export function sha256b64url(input: string): string {
  return b64url(createHash("sha256").update(input).digest());
}

Step 4 — Carry the verifier safely (signed state)

The code_verifier and nonce minted at sign-in must be available at the callback. CoLab signs them into state with HMAC-SHA256 and a 10-minute TTL, so it works across multiple backend instances with no shared storage. Same file:

const STATE_TTL_MS = 10 * 60 * 1000;
export function createSsoState(payload: { v: string; n: string }): string {
  const body = Buffer.from(
    JSON.stringify({ v: payload.v, n: payload.n, e: Date.now() + STATE_TTL_MS }),
  ).toString("base64url");
  const sig = createHmac("sha256", config.sso.stateSecret).update(body).digest("base64url");
  return `${body}.${sig}`;
}
export function parseSsoState(state: string): { v: string; n: string } | null {
  const dot = state.lastIndexOf(".");
  const body = state.slice(0, dot), sig = state.slice(dot + 1);
  const expected = createHmac("sha256", config.sso.stateSecret).update(body).digest("base64url");
  const a = Buffer.from(sig, "base64url"), b = Buffer.from(expected, "base64url");
  if (a.length !== b.length || !timingSafeEqual(a, b)) return null; // forged
  const parsed = JSON.parse(Buffer.from(body, "base64url").toString("utf8"));
  if (!parsed.e || parsed.e <= Date.now()) return null;              // expired
  return { v: parsed.v, n: parsed.n };
}

Step 5 — Build the authorize URL (with the claims request)

buildLoginRedirect() in ssoService.ts. The claims parameter asks the IdP for the full profile pack in both the id_token and /userinfo; null means "requested, not essential" (OIDC Core §5.5).

const PROFILE_CLAIMS_REQUEST = JSON.stringify({
  id_token: { email: null, email_verified: null, name: null, picture: null,
              department: null, employee_id: null, claims_jwe: null,
              products: null, entitlements: null },
  userinfo: { email: null, email_verified: null, name: null, picture: null,
              department: null, employee_id: null, claims_jwe: null,
              products: null, entitlements: null },
});

export async function buildLoginRedirect(args: { state; nonce; codeChallenge; loginHint? }) {
  const { authorizeUrl } = await resolveEndpoints();   // SSO_AUTHORIZE_URL | SSO_BASE_URL + /authorize
  const qs = new URLSearchParams({
    response_type: "code",
    client_id: c.clientId,
    redirect_uri: c.redirectUri,
    scope: c.scope,
    state: args.state,
    nonce: args.nonce,
    code_challenge: args.codeChallenge,
    code_challenge_method: "S256",
    claims: PROFILE_CLAIMS_REQUEST,
  });
  if (args.loginHint) qs.set("login_hint", args.loginHint);   // IdP launcher hand-off
  return `${authorizeUrl}?${qs.toString()}`;
}

Step 6 — Sign-in endpoint (the redirect)

backend/app/src/routes/auth.ts — GET /api/auth/sso/start. One hop: mint PKCE + signed state + nonce and redirect straight to /authorize. The IdP shows its own login page; no pre-login logout bounce.

router.get("/sso/start", async (req, res) => {
  if (!sso.ssoConfigured()) return res.redirect("/?sso_error=not_configured");
  const loginHint = sso.cleanLoginHint(req.query.login_hint);        // email-shaped or dropped
  const verifier      = sso.randomString(48);
  const codeChallenge = sso.sha256b64url(verifier);
  const nonce         = sso.randomString(16);
  const state         = sso.createSsoState({ v: verifier, n: nonce });
  return res.redirect(await sso.buildLoginRedirect({ state, nonce, codeChallenge, loginHint }));
});

The UI triggers it with a full-page navigation — no client-side OAuth logic. frontend/app/src/components/LoginScreen.tsx (the sign-in method menu, "Email" / "SSO"):

const startSso = () => { window.location.assign(api.ssoStartUrl()); };   // → /api/auth/sso/start

Step 7 — Callback: exchange, verify, decrypt

The IdP redirects the browser to the app root with ?code&state. CoLab is a SPA, so there is no server route at the redirect URI: the boot effect in frontend/app/src/components/colab/session/useCoLab1.tsx reads the two params, strips them from the address bar (so a refresh cannot replay the single-use code), and POSTs them exactly once:

// useCoLab1.tsx — boot
const p = new URLSearchParams(window.location.search);
const code = p.get("code"), state = p.get("state");
strip();                                   // remove code/state/error/login_hint from the URL
api.ssoCallback(code, state)               // POST /api/auth/sso/callback { code, state, deviceId }
  .then(({ token, user, refreshToken }) => {
    localStorage.setItem("colab.authMethod", "sso");   // logout later also ends the IdP session
    authSuccess(token, user, refreshToken);            // token → localStorage / keychain, app opens
  });

Server side, POST /api/auth/sso/callback → completeSsoCallback() in ssoService.ts:

const parsed = sso.parseSsoState(state);                 // 400 SSO_STATE_MISMATCH if forged/expired
const tokens = await exchangeCode(code, parsed.v);       // POST /token: code + code_verifier + client_secret
let claims   = await verifyIdToken(tokens.id_token, parsed.n);
//   RS256 signature via /jwks (kid-matched, refetched once on rotation),
//   aud = client_id, iss ∈ {SSO_ISSUER, base-URL origin, …}, exp (60 s tolerance), nonce
if (claims.claims_jwe) {
  const pii = await decryptClaimsJwe(claims.claims_jwe);  // RSA private PEM → { email, name, picture, department, employee_id }
  claims = { ...claims, ...pii };                          // decrypted values WIN over plaintext
}
const email = claims.email.toLowerCase();                 // the account key
return { email, name, groups, picture, department, employeeId };
// → ssoLogin(): find-or-create the (passwordless) user, picture seeds avatarUrl,
//   mint the app JWT + refresh token → res.json({ token, user, refreshToken })

Failures are surfaced to the login screen with the real reason (token-exchange status, issuer mismatch with the value the IdP stamped, missing JWE key, …) so misconfiguration is diagnosable without server logs.

Step 8 — The local session

CoLab does not use a handoff URL: the app JWT comes back in the JSON body of the callback POST and is stored by frontend/app/src/lib/tokenStore.ts (localStorage on web, OS keychain on desktop). The session is bound to the device's E2EE identity (deviceId in the callback body), so encrypted history works on that device. The user record carries the full profile: name, avatar from picture, and the SSO badge (ssoEnabled). New SSO users are created without a password and can only sign in via SSO; an existing password account with the same email is reused, never clobbered.

Step 8c — Profile claims and the encrypted PII pack v3

Read profile only after the id_token is verified (signature, iss, aud, exp, nonce). Claims CoLab requests and uses:

Claim Source Used for
emailclaims_jwe (preferred) / plaintext / preferred_usernameAccount key (lower-cased). Required.
nameclaims_jwe / plaintext / given_nameDisplay name + initials on first sign-in.
pictureclaims_jwe / plaintext (https URL only)Seeds avatarUrl for a new user.
department, employee_idclaims_jwe / plaintext (staff accounts)Carried on the SSO profile (department, employeeId).
groups / rolesplaintext, if the IdP sends themOptional org role mapping (SSO_GROUP_ROLE_MAP).
claims_jweid_token (requested via claims)Decrypted to { email, name, picture, department, employee_id }; overrides the plaintext fields.

Plaintext switch-off: when the SSO team sets profile_plaintext_claims = 0, CoLab keeps working because it prefers the encrypted channels. Resolution order (completeSsoCallback): verified id_token → /userinfo if the id_token has no identity → decrypt Fernet *_enc with SSO_PROFILE_ENC_SECRET → decrypt RSA claims_jwe → decrypted values win over plaintext. A login that still has no email fails with the claim keys received and the likely cause (public key not yet registered, Fernet secret missing, or no profile claims enabled for the client).

// ssoService.ts — Fernet (AES-128-CBC + HMAC-SHA256) on Node crypto, no dependency
export function fernetDecrypt(token: string, secret: string): string {
  const raw = createHash("sha256").update(secret, "utf8").digest();   // key = SHA256(secret)
  const sign = raw.subarray(0, 16), enc = raw.subarray(16, 32);
  const buf = Buffer.from(token, "base64url");                         // 0x80 | ts(8) | iv(16) | ct | hmac(32)
  const body = buf.subarray(0, buf.length - 32), mac = buf.subarray(buf.length - 32);
  if (!timingSafeEqual(mac, createHmac("sha256", sign).update(body).digest())) throw new Error("Fernet HMAC mismatch");
  const d = createDecipheriv("aes-128-cbc", enc, buf.subarray(9, 25));
  return Buffer.concat([d.update(buf.subarray(25, buf.length - 32)), d.final()]).toString("utf8");
}
// resolveEncClaims(): every <field>_enc → <field> (decrypted wins); no-op without SSO_PROFILE_ENC_SECRET

RSA claims_jwe — key exchange and decryption

Generate the pair once per environment (scripts/gen-sso-keys.sh wraps exactly these commands and refuses to overwrite an existing pair):

openssl genrsa -out keys/collab_private.pem 2048
openssl rsa -in keys/collab_private.pem -pubout -out keys/agenxchange_public.pem
  • Give the SSO team keys/agenxchange_public.pem (header BEGIN PUBLIC KEY, body starts MIIBIjANBg…). Safe to send.
  • Keep keys/collab_private.pem on the CoLab server only (SSO_JWE_PRIVATE_KEY_FILE, or inline via SSO_JWE_PRIVATE_KEY). keys/*.pem is git-ignored. Both PEM formats work (BEGIN RSA PRIVATE KEY from OpenSSL 1.x/LibreSSL, BEGIN PRIVATE KEY from OpenSSL 3.x).
  • Never regenerate on a server once the public key has been registered — the pair must stay matched or every SSO login fails with a decryption error.

decryptClaimsJwe() in ssoService.ts — the Node twin of the SSO team's Python reference:

import { createPrivateKey } from "crypto";
import { compactDecrypt } from "jose";

export async function decryptClaimsJwe(compact: string): Promise<SsoPii> {
  const key = loadJwePrivateKey();            // SSO_JWE_PRIVATE_KEY (raw/base64 PEM) or *_FILE; cached
  if (!key) throw ssoErr(500, "id_token carries encrypted claims (claims_jwe) but no SSO_JWE_PRIVATE_KEY / SSO_JWE_PRIVATE_KEY_FILE is configured.");
  const { plaintext } = await compactDecrypt(compact, key, {
    keyManagementAlgorithms: ["RSA-OAEP", "RSA-OAEP-256", "RSA-OAEP-384", "RSA-OAEP-512"], // RSA1_5 refused
  });
  return JSON.parse(new TextDecoder().decode(plaintext));   // { email, name, picture, department, employee_id }
}

Fails closed. No key configured, wrong key, tampered ciphertext, unsupported algorithm or a non-JSON payload all reject the sign-in with a message naming the problem. CoLab never falls back to plaintext claims when claims_jwe is present. Covered by unit tests in backend/app/test/sso.test.ts.

Step 9 — Logout (clear both sessions)

Logging out must end the CoLab session and the IdP's SSO cookie; otherwise the next "SSO" click silently re-authenticates.

User confirms Logout (CoLab)                       useCoLab0.tsx doLogout()
  → POST /api/auth/logout  (revoke JWT + device session, close sockets)
  → clear token / refresh token / drafts / local state
  → if localStorage colab.authMethod === "sso":
       window.location.assign("/api/auth/sso/logout")   routes/auth.ts
  → 302 https://stgoa.re.cx/logout?post_logout_redirect_uri=<app root>&client_id=collab
  → IdP clears its cookie, then sends the browser back to <app root> (sign-in screen)
  → next SSO sign-in asks for credentials again

Local state is cleared before the navigation, so no re-render can cancel the IdP logout trip. This is the only place CoLab calls the IdP /logout; SSO start goes directly to /authorize.

Security rules (non-negotiable)

  • PKCE S256 on every sign-in — even with the client secret.
  • IdP only over HTTPS (https://stgoa.re.cx/).
  • redirect_uri is the configured app root — never reflected from user input.
  • state is HMAC-verified with a 10-minute TTL and carries the PKCE verifier + nonce.
  • id_token validated (JWKS signature, iss, aud, exp, nonce) before any claim is trusted; claims_jwe is decrypted only from a verified token.
  • Fails closed: unverifiable signature or undecryptable claims_jwe rejects the login. SSO_INSECURE_SKIP_VERIFY is refused in production.
  • Client secret, state secret and the JWE private PEM stay server-side (env / mounted file) — never in the browser or in git.
  • Only the public PEM is shared with the SSO team.
  • The app JWT is returned in a POST body, never in a URL; the one-time code is stripped from the address bar immediately.
  • Logout completes the IdP /logout redirect before the sign-in screen is shown again.
