1. Project overview

What it is. CoLab (branded "Collab") is an enterprise team-collaboration platform in the Slack/Teams class: real-time messaging (DMs, groups, threads, reactions, scheduled messages, forwarding), 1:1 calls and group huddles, scheduled meetings with lobby, polls, hand-raise, screen share, recording, a collaborative whiteboard, file sharing, tasks, reminders, calendar, presence, notifications (in-app, web push, FCM, APNs VoIP), organisations with RBAC, SSO (OIDC), MFA, and an optional end-to-end-encryption layer. It is deployed at a single corporate tenant (collab.resulticks.com) and shipped as a web app plus Windows/macOS/Linux Electron desktop clients that load the hosted web app.

Application type and platforms

  • Type: authenticated single-page application. The Next.js server only serves the static shell and reverse-proxies /api, /socket.io and /livekit to the backend and SFU. There are no Next route handlers, no server components with data, and SSR is explicitly disabled for the app (frontend/app/src/app/page.tsx).
  • Platforms: browsers (Chrome/Edge/Firefox/Safari 16.4+), Windows (NSIS installer and portable exe), macOS (pkg/dmg, universal), Linux (AppImage/deb). Mobile apps are out of this repo but served by the backend push services (FCM, APNs VoIP).
  • Dev vs prod: dev runs tsx watch backend on :4000 and next dev on :3002 with Docker for MySQL/Redis/MinIO/LiveKit. Prod runs next start (:3000) and tsx backend (:4000) in containers behind nginx (:7530 internal, :7524 published on the live host) or Caddy, with LiveKit/coturn media ports published directly.

High-level architecture summary

The system is a classic three-tier chat platform with a realtime plane: a client-only React SPA keeps all state in one hook chain and talks to a single Express/Socket.IO process over same-origin REST and WebSocket; that process owns MySQL (raw SQL), Redis, file storage and LiveKit token issuance; media flows peer-to-SFU. The desktop apps are browsers in a native frame. The architecture is functionally rich and operationally hardened (health checks, leader election, graceful shutdown, retries, storage fallbacks), but structurally it is a set of very large monoliths: a 300-key untyped session bag on the client, 5k-line components, an 8k-line SQL driver, and a 2.8k-line Electron main file. There is no offline mode and no document editor; the "editors" are the TipTap chat composer and a whiteboard with last-writer-wins snapshots.

Persistence and synchronisation

  • localStorage: tokens (clb_token, clb_refresh; desktop mirrors them into the OS keychain), clb_mode, clb_theme, drafts clb_draft_<convId>, UI prefs (clb_nav_collapsed, clb_spatial_audio, clb_call_view_mode…), E2EE bookkeeping (e2ee_device_id, e2ee_recovery_*), clb_admin_token; sessionStorage holds clb_ops_token and clb_started_calls.
  • IndexedDB: signal-store (identity, prekeys, sessions, sender keys, plaintext cache, replay log), signal-epochs, colab-media-cache (decrypted attachments, LRU, 350 MB budget).
  • Server sync: socket events update state directly; most domains also refetch on their change event (TASK_CHANGED → refetchTasks), so a create does a POST and then a full list GET, and the socket echo triggers a second GET.
  • Cross-tab: token rotation is coordinated through the localStorage mirror (409 from refresh → wait for sibling tab to write the new token).

Architectural problems found

  • CRITICAL Untyped session bag. Every CoLabSessionN and CoLabSessionShell field is any (CoLabShell.tsx lines 60–140 declare ~300 any fields). tsconfig has strict:false. Refactors cannot be verified by the compiler.
  • CRITICAL Whole-app re-render on any state atom. CoLabV1.tsx spreads seven objects into a new s every render; CoLabShell is not memoised and passes ten inline lambdas to ChatView, so React.memo on views never hits.
  • HIGH Duplicate state via shadow refs. ~20 refs (meRef, modeRef, activeIdRef, conversationsRef, messagesByConvRef, settingsRef, tokenRef…) mirror state by hand; the access token exists in four places (ref, localStorage mirror, keychain, socket.auth).
  • HIGH Prop drilling of 8 levels. onReact: useCoLab4 → CoLabV1 → CoLabShell → ChatView → useChatView0/1/2 → ChatViewShell → ChatColumn → ChatMainPane → MsgRow → MessageHoverToolbar. ChatView mirrors the same pattern with its own useChatView0..2 and s bag.
  • HIGH Socket lifecycle tied to callback identity. The useCoLab2 effect depends on 17 callbacks; if any changes identity, the socket is closed, re-created and the bootstrap fetches run again.
  • MEDIUM Hidden side channels. A window.dispatchEvent bus with 11 event names (colab:toast, colab:unauthorized, colab:org-invalid…) and module-level singletons in lib/dialog.ts, lib/studio.ts, lib/errorReporter.ts, lib/e2ee/manager.ts (which holds the token and keys at module scope).
  • MEDIUM Circular hook contracts. Later segments receive setters from earlier ones and earlier segments call later ones through refs (loadMessagesRef, refetchTasksRef, onLeaveRoomRef), which is the manual way of breaking an ordering cycle.

HTTP client (frontend/app/src/lib/api.ts)

  • Transport: native fetch; base URL is NEXT_PUBLIC_API_BASE_URL || "" (same origin by design, so no CORS in production). uploadFile uses XHR for progress and supports AbortSignal.
  • Headers: Authorization: Bearer only when the caller passes token (every call site passes tokenRef.current), plus X-CoLab-Device-Id from localStorage.
  • Retry: GET only, one retry after 600 ms on network error/429/5xx; writes are never retried. No request timeout or cancellation on ordinary requests.
  • 401 handling: a 401 on an authenticated call re-validates with /api/auth/me; a confirmed 401 runs a single-flight POST /api/auth/refresh (12 s timeout, 409 means a sibling tab is rotating → poll the localStorage mirror for 2 s). Success dispatches colab:token-refreshed; failure clears the refresh token and dispatches colab:unauthorized → logout. The original failed request is not replayed.
  • Errors: throws Error with .status/.code/.details from the {ok:false,error} envelope; ORG_MEMBERSHIP_INVALID → colab:org-invalid. Failures are logged to the diagnostics ring buffer and telemetry.
  • Surface: one flat object with ~262 methods and untyped parameters. Groups: auth, orgs (~30), sessions, users/invites/blocks, conversations/messages, files, meetings (~45), calls, reminders, tasks (~35), e2ee (~30), notifications, push, telemetry, ai. adminApi.ts is a second client for /api/admin. Fifteen raw fetch( sites bypass both (Rail, UpdateWatcher, VoicePlayer, FileAttachment, MediaAlbum, DownloadModal, useCoLab4, downloadAttachment, DevPortal).

Backend HTTP chain (backend/app/src/app.ts)

Request id → security headers (HSTS in prod) → CORS allowlist (loopback and RFC1918 reflected outside prod) → per-path brute-force limiters (login/signup/SSO/token 30 per 15 min) → global limiter 600/min keyed by JWT subject or IP (in-memory per process) → raw body for the LiveKit webhook → JSON 5 MB (uploads stream) → optional redacted debug log → 33 routers mounted under /api → 404 → error handler that persists to error_logs and maps MySQL errno 1062/1451/1452 and SIGNAL 45000 to 4xx. Auth is applied per router (router.use(authMiddleware)), with deliberate public endpoints only for file links/tickets, sticker/GIF proxies, public avatars, health, telemetry ingest and webhook ingest.

Realtime (backend/app/src/realtime/socket.ts)

  • Single namespace, rooms conv:<id>, user:<id>, session:<jti>, meeting:<id>. Redis adapter when REDIS_URL is set, in-memory fallback after a 3 s gate.
  • Client→server: conversation:join, message:send, message:react, typing, call:request/accept/decline/cancel/hangup, huddle:*, meeting:join/hand/reaction/chat/takeover, devices:list, handoff:*, wb:save/load.
  • Server→client: message:new/updated/deleted/read, conversation:*, presence:update, call:*, meeting:*, notification:*, task:changed, reminder:changed, file:changed, session:revoked, org:membership-revoked, six e2ee:* events, server:restarting.
  • The frontend EVENTS map in lib/socket.ts is a hand-maintained copy of shared/src/events.ts and has already drifted (meeting:lobby:update, meeting:presence, and raw strings such as "wb:save", "call:error", "message:rate_limited").
  • Polling: none for core data, but views poll where a socket event would do: OrgAdmin 5 s, MeetingRoom lobby 5 s and 20 s, PreJoinMeeting 5 s, CalendarView 10 s, Settings concerns 30 s. No Server-Sent Events.

20. Final architecture report

A. Current architecture in simple terms

A browser (or an Electron window pointing at the same URL) downloads a Next.js shell and renders one big React application entirely on the client. That application keeps everything it knows in a chain of seven hooks and passes the result down as one object. It talks to a single Node process over same-origin REST calls and a Socket.IO connection, both proxied by Next and nginx. That Node process authenticates with JWTs and sessions, writes to MySQL through hand-written SQL, uses Redis for fan-out and caches, stores files on disk then MinIO then MySQL, mints LiveKit tokens so browsers can exchange audio/video with a self-hosted SFU, and runs timers for reminders and clean-up. Nothing works without the server.

B. Top 10 architecture problems

  1. Push credentials and a TURN secret committed to git (§7, §17).
  2. No CI gate on the branch that is deployed; manual builds on the production host (§10).
  3. Untyped ~312-key session bag and seven god hooks; strict:false (§5).
  4. Memoisation defeated in the message list and shell (every keystroke re-renders all rows) (§13).
  5. Two duplicated LiveKit lifecycles inside 5.4k- and 2.5k-line files (§8).
  6. Fail-open authentication checks, weak default admin password, escrow key derived from the JWT secret (§7).
  7. No offline support, no outbox, service worker caches nothing (§12).
  8. 36k-line global CSS with ≥24% dead rules and two token systems (§13).
  9. No data-access layer: 43 components call a 262-method untyped API object; socket contract hand-copied and drifted (§6, §16).
  10. Backend monoliths (8.2k-line SQL driver, 1.7k-line socket file) and in-memory state that breaks with two replicas (§17).

How the application works end to end

Startup: the backend boots, migrates MySQL, elects a scheduler leader and listens on :4000; Next serves the shell on :3000 behind nginx. UI: the browser renders CoLabV1 client-only; CoLabShell shows splash, login or the app. State: seven hooks hold everything and hand it to views as one object; views mutate it through handlers that call REST (lib/api.ts) or emit on the socket. API: same-origin /api and /socket.io are proxied to Express, which authenticates the JWT, checks session/device/org, dispatches to a service, runs raw SQL, and broadcasts a socket event that the client reconciles against its optimistic state. Editor: the TipTap composer produces sanitised HTML; the whiteboard syncs strokes over the LiveKit data channel and snapshots to MySQL every 1.5 s. Storage: files go disk → MinIO → MySQL blob; decrypted media is cached in IndexedDB; tokens in localStorage or the OS keychain. Deployment: two Docker images built on the host by docker compose, nginx in front, LiveKit and coturn exposed for media; desktop builds from Azure load the same URL and update themselves from a static manifest.
